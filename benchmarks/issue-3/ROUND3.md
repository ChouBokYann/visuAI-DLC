# Local scale, resources, freshness and scored comparison

**Recommendation: use Graphify with a small deterministic compatibility view for the first project-understanding prototype.** Keep canonical Markdown/YAML authoritative. Retain codebase-memory-mcp as a code-indexing candidate; its Linux code indexing was faster here, but its document retrieval over the Windows bind mount was slow. Basic Memory passed the correctness tests but did not finish the 5,000-document initial index within this run's ten-minute limit.

This changes the provisional recommendation in round 2 because we now measured complete retrieval workflows, larger corpora, and update behavior. These are findings about the tested local configurations, not universal product rankings. No model API calls, embeddings, paid extraction, or host ACL changes were used.

## Scores on the same small project scenario

The [rubric](SCORING.md) was fixed before the scale runs. Speed, completeness, and controlled correctness receive equal weight. Speed uses the p95 of **20 warm complete workflows**, following one initial workflow. Each small workflow retrieves the same six fact-relevant documents; server startup is excluded. Graphify discovers outgoing and incoming relationships then reads their source files; Basic Memory discovers relationships and reads notes through MCP; CBM searches source and follows declared YAML references through its source-reading API.

| Workflow | Complete retrieval p95 | Speed /5 | Completeness /5 | Correctness checks /5 | Mean /5 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Graphify + declared-edge view + source reads, Windows | 11.5 ms | 5 | 5 (12/12 facts) | 5 (8/8 checks) | **5.0** |
| codebase-memory-mcp + YAML reference following, Linux container | 179.8 ms | 3 | 5 (12/12 facts) | 5 (8/8 checks) | **4.3** |
| Basic Memory + native-link view, Windows | 667.3 ms | 2 | 5 (12/12 facts) | 5 (8/8 checks) | **4.0** |

This is not a claim of perfect general accuracy. All three tied on the twelve frozen document facts and eight controlled checks: metadata fidelity, source provenance, pending status, replaced relationships, deleted documents, stable-ID rename, changed evidence outcome, and preserved inference metadata. The checks are agent-authored executable checks, not independent human grading or LLM-answer evaluation. A score of 5 means passing this bounded rubric.

[round3-scores.json](round3-scores.json) is generated by [score_round3.py](score_round3.py); it retains each individual check. Full responses, paths, payload hashes, call counts and timings are in `raw/*workflow*responses.json`. The matched small runs exclude procedure/release bodies because the questions need their identifiers but not those bodies. Earlier broader runs remain saved separately.

## Scale results

The document stress fixture contains 5,000 small documents, about 3.87 MB, arranged as 1,000 independent five-document threads: goal, capability, feature, decision, evidence. It has 4,000 declared relationships. It does not model a heavily interconnected production graph or 5,000 long design documents.

| Measurement | Graphify + compatibility view | Basic Memory + compatibility view | CBM, Linux container |
| --- | ---: | ---: | ---: |
| Initial 5,000-document preparation/index | 10.11 s projection to native graph JSON | 19.29 s projection; initial index **timed out at 600 s** | 45.47 s native index |
| 5,000-document complete retrieval p95 | **104.98 ms** | Not measured on a complete index | **19.94 s** |
| 5,000-document speed score | 3/5 | N/A | 1/5 |
| 100-document complete retrieval p95 | 12.31 ms | 690.22 ms | Not run at this size |
| 1,000-Python-file native indexing | 38.26 s | Not an AST indexer in this test | **8.62 s** |

Graphify's document timing is a deterministic projection of already-authored relationships into its supported node-link graph format. It is **not** semantic document extraction and is not equivalent work to Basic Memory's or CBM's broader indexing. CBM scanned the unmodified canonical Markdown at baseline; its document source reads correctly expose the YAML relationships even though they are not native business-meaning edges in its AST graph.

After the Basic Memory timeout, the isolated database contained 2,699 of the 5,000 Markdown entities. This establishes a time-budget miss on this machine, not an inability to support 5,000 notes. The process was stopped, observations retained, and later small-project checks passed. No complete-index query score is assigned to that run. A Windows output-handle cleanup error occurred after the profiler had saved its timeout result; the profiler now waits for terminated children and tolerates a temporarily locked display log. A timeout self-check passes.

CBM's 5,000-document workflow uses `search_code` over a Windows-mounted corpus and then source reads. Its median was 17.33 s and p95 19.94 s, versus 179.8 ms p95 on the small fixture. Do not attribute this entirely to the native C engine: filesystem/VM boundaries and full source searching differ from a loaded graph traversal. The code indexing result demonstrates why CBM should remain a separate code candidate.

There is no combined 5,000-document quality score: the quality oracle covers the frozen small questions and mutation scenarios, not exhaustive human review of the stress corpus. The scale fixture deliberately omits dangling references to omitted procedure/older-decision records, so it is not the exact small answer-key scenario repeated unchanged.

These are different counters and scopes, so they are **not an apples-to-apples RAM ranking**. Idle-server power/CPU was not separately profiled.

The 5,000-node Graphify JSON was 2.48 MB. The shared Basic Memory database was 25.05 MB after several fixtures and the partial stress run; CBM's shared cache was 38,244 KiB after code and document projects. These storage figures cover different datasets and are descriptive only.

## Changes, deletes, renames and history

Both document MCP sessions stayed alive while the 100-note corpus changed. The scenario replaced a feature's capability edge, renamed its canonical file while retaining its ID, deleted a decision, changed evidence from pending to failed with a new tested revision, and added an explicitly inferred edge.

- Graphify's view update took 0.475 s. Its running MCP session returned the new edge and no deleted decision. Canonical filenames can change because the derived view uses stable-ID filenames.
- Basic Memory's projection update took 0.819 s and native incremental indexing took 5.486 s. The command reported **3 indexed, 1 deleted**, rather than reindexing all notes. Its existing MCP session returned the changed evidence and rejected the deleted note.
- Both indexes contained exactly the expected **79 declared relationships** after the update. Inferred metadata remained in Markdown and was not silently promoted into either declared-edge view.
- CBM's separate 5,000-document update used the same stable-ID view convention. Projection took 6.918 s; the native reindex call took 31.500 s. Source retrieval reflected the replaced relationship, renamed canonical record's stable ID, failed evidence and inference flag; the deleted decision was absent. This test does not claim a three-file-only internal CBM indexing pass.
- In the 1,000-file code corpus, Graphify explicitly reported **3 changed, 997 unchanged, 2 deleted** and updated in 6.350 s. CBM's reindex call took 7.389 s. Both passed deletion, rename, addition and changed-source checks: **8/8 native-code checks** across the two tools.

Historical retrieval deserves separate handling. A controlled white-box probe temporarily aged five synthetic Basic Memory entity rows to 2020, queried with `since=365d`, and restored their original timestamps. The filtered context returned no related edges, while direct reading still succeeded. This is not data loss or an incorrect application of the requested filter; it shows that a date-filtered context call is insufficient for our all-history understanding task. The probe only ages entity timestamps, not every internal read-model timestamp. A production Basic Memory integration needs a tested unfiltered/reference-following path for old decisions. Graphify and CBM's tested retrieval paths did not request a recency filter.

## Reuse and compatibility scope

[project_fixture.py](project_fixture.py) reuses the repository's strict frontmatter reader and validator. It projects declared edges into native Basic Memory links or Graphify's graph format, preserves provenance and inference flags in canonical metadata, uses stable IDs for derived filenames, and removes only previously recorded generated files inside `.bench-run`. It compares parsed content so Basic Memory's added permalink/YAML formatting does not cause wholesale rewrites. CBM's workflow follows declared references from retrieved YAML; its update view also uses stable-ID filenames.

This is benchmark implementation, **not a released production adapter or ideation skill**. Concurrent-writer conflict handling, atomic multi-file publication, real project migrations, long-document retrieval budgets and independent comprehension review still need acceptance criteria before production adoption. No source documents in the repository were rewritten by the benchmarks.

## Reproduction and validation

Use a fresh isolated run directory; scripts refuse to overwrite observations. The original setup uses `.bench-run/bm-venv` for MCP/psutil/PyYAML and `.bench-run/graphify-mcp-venv` for Graphify's MCP extra. Main steps:

1. Generate 100 and 5,000 document fixtures with `project_fixture.py generate --count N`; run `scale_setup.py N` to profile projections and Basic Memory setup/indexing. The original 100-note views were separately profiled first, so that run used `--views-exist`.
2. Run `run_document_queries.py`. `workflow_probe.py` supports individual cases and preserves 21 trials. The matched small runs use the final type-filtered workflow; the broader initial small runs remain as prior observations.
3. Run `freshness_session.py` and `history_probe.py` against the isolated 100-note project.
4. Generate the code corpus with `code_scale.py generate`; index Graphify with `extract --code-only --no-cluster --max-workers 1`, mutate with `code_scale.py mutate`, then rerun extraction.
5. For CBM, use the official portable Linux archive and Ubuntu 24.04 container described below, with a read-only fixture mount, `--network none`, `--cap-drop ALL`, `--security-opt no-new-privileges`, read-only root and writable temporary `/tmp`. The saved plans drive small, scale and update MCP calls. `capture_environment.py` runs before container teardown.
6. Run `score_round3.py` after the observations and final derived views exist; run `python -m unittest discover -s tests` for structural and compatibility tests.

Ubuntu image digest: `sha256:fe81560990fae86dc4743202b2cb4d3df98d0bcf949173cecef15ce1127ef852`. The container used `CBM_CACHE_DIR=/tmp/cbm-cache`, `HOME=/tmp/home` and `sleep infinity`; MCP sessions ran `/work/codebase-memory-mcp` through `docker exec -i`. It has been stopped and removed. Host fixtures and raw results are retained; no benchmark server is left running.

Validation: 12 repository tests pass; 12/12 document-fact checks and 8/8 document-correctness checks pass per workflow; exact declared-edge equality passes; all 8 code-update checks pass; profiler timeout handling self-check passes. These are local deterministic tests. There is no claim of independently graded generated answers, realistic large-project semantic extraction, long-document performance or production concurrency readiness.
