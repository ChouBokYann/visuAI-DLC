## Shared outcome

A visitor can save up to three unique cafés while browsing search or a story result's details, compare their existing café facts, remove a saved café and add a replacement, and recover the selection after a normal reload. Bad/stale stored data cannot break the experience or introduce invented café data. When browser storage is unavailable, the visitor can still use a temporary selection and receives understandable feedback about the persistence limitation. The existing story and search still work. Controls work with a keyboard and at a 390 px mobile viewport.

## Test setup and evaluation rules

- Use the same installed browser executable and version, automation library, host, and viewport for both candidates; record them. Desktop 1440×1000, mobile 390×844, device scale factor 1. Use fresh isolated browser contexts per independent storage case and a separate origin per candidate. Test candidates sequentially.
- Use actual rendered browser controls for journeys. Locator text may vary; adapt locators to each UI without changing expected outcomes or requiring particular component structure, labels, storage key/schema, sorting, colors, or interaction count. Record storage keys by observing before/after state when saving; read code only if necessary to set an equivalent failure fixture after criteria are frozen.
- Use a clean context initially. Capture console/page errors and screenshots of populated desktop comparison, capacity feedback, temporary-storage feedback, and mobile comparison. Record steps and observed outcomes for every case. A screenshot alone is insufficient for persistence or keyboard claims.
- Report each criterion PASS, FAIL, or UNVERIFIED, with evidence. Do not substitute developer-written tests for browser acceptance. Existing tests/build provide supplementary regression evidence. Distinguish any baseline failure from a newly introduced regression.
- No external café research or new live facts. Compare content against the baseline fixture below and the frozen commit's `src/cafes.ts`. Do not claim menus, opening hours, locations, or availability have been independently revalidated.
- A comparison may be a page, panel, dialog, or another understandable surface. It must expose each saved café's required fields together without needing to open one café detail at a time. Local horizontal scrolling inside a clearly usable comparison region is acceptable on mobile; page-wide horizontal overflow is not.
- Limit is three distinct café IDs. Repeating a save must not produce a duplicate. A deliberate toggle/removal is acceptable if clearly labeled; an accidental save retry must not silently remove a café. At capacity, a fourth save must preserve the current three and explain how to remove/replace one, unless a clearly deliberate replacement flow is used. Do not demand a one-click replace feature: remove then save satisfies replacement.
- Normal reload persistence is required; cross-device sync and cross-tab concurrency are out of scope. No persistence is promised when browser storage access fails. Malformed-state recovery may preserve sanitized valid entries or reset to a safe empty state; it must not render unknown cafés, exceed the limit, retain duplicates, or crash.
