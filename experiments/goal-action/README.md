# Goal-to-action pilot: preregistered protocol

Owner: ChouBokYann. Date: 2026-11-23. User authorized the next bounded test following context-handoff/RESULTS.md. Local synthetic trial only; no claim of other-maintainer approval or adoption on main. This document records the local proposal and scope before execution. Prior related issue search found no overlapping ontology/handoff issue. No publication is authorized.

## Question and scope

Does relevant domain guidance help a producer turn an underspecified goal into concrete obligations, and does a fresh consumer preserve those obligations through implementation and changed requirements? Compare two conditions, one task, one producer and one consumer per condition. G receives generic process guidance; D receives community-class selection knowledge of exactly the same whitespace-word length. Common inputs, source facts, starter code and execution limits remain identical.

The synthetic task is a community workshop finder. A beginner wants classes they can actually attend, with supplied availability and catalogue facts. Initial artifacts are functional but incorrectly mark every workshop available. Both consumers implement a bounded local correction. Then both receive the same new availability/access requirement and a stale historical status memo. No further answer feedback, grader diagnostics or repair rounds are given. At most one setup retry for tool/file failures, not reasoning or code defects. No new packages, web access, production deployment or changes to real apps/core skills.

Reuse Python, Node and the existing Playwright installation from experiments/coffee-atlas. Parent owns protocol, generator, evaluator and output evidence. Producers own only their assigned HANDOFF.md; consumers own only app.mjs, index.html and DELIVERY.md in their arm. Data changes for the predetermined second phase belong to the parent. Agents are not alone and must not read or edit other arms or oracles. Agent calls use inherited settings, no model override. No direct paid API purchases; normal session usage still applies.

## Procedure

1. Generate/freeze two packets, source facts and identical starter artifacts. Confirm exact guidance word-count matching and byte hashes. Run the independent tests against the starter to establish that all-available behavior fails.
2. Two fresh producers read only their packet and source files, then write concrete bounded handoffs with goal/source links, inferred needs and evidence requirements. They cannot implement or see each other's work.
3. Two fresh consumers read their handoff, original request, source data and common execution constraints. They do not receive the producer's extra guidance. Each implements phase 1 and reports scope/evidence. Parent archives files and performs independent function and browser checks without returning results to agents.
4. Parent changes availability from 10:00–14:00 to 10:00–13:00 and adds a requirement for confirmed step-free access. Both consumers receive that update and a clearly historical memo carrying the former preferences and a readiness statement. They implement phase 2 without grader feedback.
5. Parent reruns the same independent checks against current preferences, captures/inspects actual pages, reviews current-state records and compares conditions. Stop and report; do not fix failed arms or change the oracle.

## Fixed assessment

Producer: (a) supplies at least two concrete decision-useful inferred conditions with explanations, rather than telling the consumer to discover them; (b) preserves goal/source and labels interpretations; (c) treats unknown facts honestly; (d) avoids booking/accounts/payment scope.

Consumer behavior: check all ten supplied classes in phase 1 and phase 2 against independent expected outcomes. Additional evaluator-only cases check exact start/end boundaries, zero capacity versus unknown capacity, and prerequisite handling. These facts/rules follow the resident's goal and the provided field definitions; evaluator expectations are not sent to agents. All cards remain visible with available/unavailable/needs-confirmation state and reasons, enabling comparison rather than hiding unknowns.

Browser: independently compare displayed states with expected outcomes, require nonempty reasons for unavailable/uncertain options, confirm the latest preference summary is rendered, no page errors or page overflow at 390/1280px. Inspect screenshots for whether the result makes the decision clear. Passing these checks is not a broad aesthetic/accessibility certification.

Adaptation: phase-2 record identifies the new goal constraints, superseded preferences and applicability limits of earlier evidence. Record unsupported completion claims or unauthorized scope expansion. Keep generated source and browser evidence separate from agent self-reports. Parent assessment is not blinded; n=1 per condition cannot establish a causal effect or general superiority.

## Method and limits

Adapt the rule-to-context idea of https://arxiv.org/html/2412.07493v1 and selective relevant knowledge from https://arxiv.org/html/2201.11332v1. No RDF engine, ontology learning, attention masking or training. Domain guidance is manually selected, so any difference may reflect useful hints, not an ontology-specific effect. Exact whitespace-word matching is not exact token/complexity matching. This exercise tests small stateful implementation, not open-ended visual craft or user satisfaction. Revisit production contracts only if an evidenced failure justifies a change.

All data is invented. The literal date supplied in fixtures denotes a synthetic day; no real schedules, venues, eligibility or access claims are made. Rollback touches only this experiment and its output. No open user decision blocks the trial.
